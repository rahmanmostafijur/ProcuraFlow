# 01: Continuous integration and dependency audit on GitHub Actions

## Issue

### Problem

Nothing verified a change before it reached `main`. The 242 backend tests, the 58 frontend tests, the type
check, the production build and the dependency audit only ran when someone remembered to run them on the
development machine. There was also no proof, other than a test that builds its own throwaway database,
that the migration chain builds the schema from an empty database in a clean environment, which is exactly
what a fresh deployment does.

### Plan

- A `CI` workflow with two jobs:
  - `backend`: Python 3.12, a `postgres:16-alpine` service, `alembic upgrade head` against the empty service
    database, then the full pytest suite.
  - `frontend`: Node 22 LTS, `npm ci`, type check, Vitest, production build.
- A `Dependency audit` workflow on push, pull request and a weekly schedule: `pip-audit` on the backend
  runtime requirements and `npm audit --omit=dev` on the frontend.
- Cancel superseded runs, read-only token, actions pinned to major versions.
- Status badges at the top of the README.

## Pull request

### What changed

- `.github/workflows/ci.yml`
  - `backend` job: `postgres:16-alpine` service (user, password and database `procuraflow`, health-checked
    with `pg_isready`), pip cache keyed on both requirements files, `procuraflow_test` created with `psql`,
    `alembic upgrade head` on `procuraflow`, then `python -m pytest -q`. `ENVIRONMENT=test`, a test-only
    `JWT_SECRET_KEY`, `DATABASE_URL` / `TEST_DATABASE_URL` pointing at the service on `localhost:5432`.
  - `frontend` job: `actions/setup-node` with Node 22 and the npm cache keyed on `package-lock.json`,
    `npm ci`, `npx tsc -b`, `npm test`, `npm run build`. A comment marks where lint and format checks go
    (task group 2).
  - Triggers: push to `main` and every pull request. `concurrency` cancels a run superseded by a newer push
    to the same ref. `permissions: contents: read`. Job timeouts (30 and 15 minutes) so a hung test cannot
    hold a runner for six hours.
- `.github/workflows/audit.yml`
  - `python` job: `pip-audit==2.10.1 --strict --desc -r backend/requirements.txt`.
  - `npm` job: `npm audit --omit=dev` in `frontend` (reads `package-lock.json`; no install needed).
  - Triggers: push to `main`, pull requests, Mondays 06:00 UTC, and manual dispatch.
- `frontend/package-lock.json`: `follow-redirects` 1.16.0 -> 1.16.1. The new audit job found two high
  advisories (GHSA-q3jh-wrc6-jgq8, GHSA-8r9p-f939-6h3c: credential headers not stripped on cross-origin
  redirects). It is a transitive dependency of axios used only by axios's Node HTTP adapter; the browser
  bundle uses the XHR adapter, so the deployed app was not exposed, but the audit has to start green
  without an ignore list. Lockfile-only change, no `package.json` change.
- `README.md`: CI and dependency-audit badges under the title.

### Why

- Migrations run against the empty service database before the tests, because the test suite itself builds
  its schema with `Base.metadata.create_all`. Without this step a migration that drifted from the models
  could pass CI and fail on the first deploy. (`tests/test_migrations.py` also does an
  upgrade/downgrade/upgrade round trip on a throwaway database; the explicit step makes the failure obvious
  in the job log and runs on the same database the app would use.)
- Python 3.12 matches the production image (`backend/Dockerfile`) and the local virtualenv. Node 22 is the
  current LTS line; local development uses Node 24, and the lockfile (version 3) installs on both.
- Only the runtime dependencies are audited for now. `pytest` 8.3.4 in `requirements-dev.txt` has a known
  advisory (PYSEC-2026-1845, fixed in 9.0.3) that task group 4 removes by upgrading to pytest 9 with a
  matching pytest-asyncio. Auditing the dev requirements today would either fail every run until then or
  need an ignore entry, and an ignore list is how advisories end up hidden for good. Task group 4 adds
  `-r backend/requirements-dev.txt` to the audit in the same change that lands pytest 9. Likewise
  `npm audit --omit=dev` leaves out the Tailwind 3 build chain advisories documented in the README; they
  never ship to the browser and go away with the Tailwind 4 redesign (task group 9).
- `--strict` makes pip-audit fail if a requirement cannot be resolved or audited, rather than skipping it.
- No end-to-end job yet: it arrives with the Playwright suite in task group 10, and a placeholder job that
  does nothing would only show a green tick for work that is not there.

### Alternatives considered

- A single workflow with the audit as another job: rejected because the audit needs a schedule of its own,
  and a failing advisory (which can appear without any code change) should not mark the code-quality
  workflow red for unrelated pull requests.
- Running the backend job inside the `docker-compose.yml` stack: slower (image build), and the compose file
  is a development setup (bind mounts, `--reload`), not a test harness. A service container gives the same
  Postgres 16 image directly.
- Dependabot or `pip-audit` via a third-party action: the plain CLI calls are pinned, readable, and identical
  to what a developer runs locally.
- Pinning actions to commit SHAs: stronger supply-chain guarantee, but major-version tags are easier to
  read and pick up fixes without churn; the token is read-only and no secrets are exposed to the workflows, which limits what a
  compromised action could do.

### New dependencies (name, exact version, why)

- `pip-audit` 2.10.1 (CI only, installed in the audit job, not added to any requirements file): checks the
  backend requirements against the PyPI/OSV advisory databases.

### Tests added or changed

None. The workflows run the existing suites.

### How to verify (exact commands)

Workflow syntax (actionlint, run through its official container image):

```bash
docker run --rm -v "$PWD:/repo" -w /repo rhysd/actionlint:1.7.7 -color=false
```

Backend job, reproduced locally against the `pf-audit-pg` container (port 55432):

```bash
docker exec pf-audit-pg psql -U procuraflow -d procuraflow -c "CREATE DATABASE procuraflow_ci"
cd backend
ENVIRONMENT=test JWT_SECRET_KEY=ci-only-secret-key-0123456789abcdef0123456789abcdef \
  DATABASE_URL=postgresql+asyncpg://procuraflow:procuraflow@127.0.0.1:55432/procuraflow_ci \
  .venv/Scripts/python -m alembic upgrade head
docker exec pf-audit-pg psql -U procuraflow -d procuraflow -c "DROP DATABASE procuraflow_ci"
ENVIRONMENT=test JWT_SECRET_KEY=ci-only-secret-key-0123456789abcdef0123456789abcdef \
  TEST_DATABASE_URL=postgresql+asyncpg://procuraflow:procuraflow@127.0.0.1:55432/procuraflow_test \
  DATABASE_URL=postgresql+asyncpg://procuraflow:procuraflow@127.0.0.1:55432/procuraflow \
  .venv/Scripts/python -m pytest -q
```

Frontend job:

```bash
cd frontend
npm ci
npx tsc -b
npm test
npm run build
```

Audit job:

```bash
python -m pip install pip-audit==2.10.1
pip-audit --strict --desc -r backend/requirements.txt
cd frontend && npm audit --omit=dev
```

The workflows themselves have not run on GitHub yet: the first real run happens when the owner pushes the
branch (GitHub Actions cannot be run from the development machine).

### Results (measured)

All measured on the development machine on 2026-10-22 (Windows 10, Postgres 16 in Docker):

| Check | Result |
|---|---|
| actionlint 1.7.7 on both workflows | no findings |
| `alembic upgrade head` on the empty `procuraflow_ci` database | all migrations applied, head `c7e2a9f4d610`, 16 tables (including `alembic_version`); database dropped afterwards |
| Backend suite (CI environment variables) | 242 passed, 2 warnings, 934.99 s |
| `npx tsc -b` | no errors |
| `npm test` | 58 passed in 12 files |
| `npm run build` | built; one JS chunk 828.40 kB (243.54 kB gzip), CSS 19.31 kB |
| `pip-audit --strict -r backend/requirements.txt` | no known vulnerabilities |
| `pip-audit -r backend/requirements-dev.txt` (not in CI yet) | PYSEC-2026-1845 in pytest 8.3.4 (fix 9.0.3), as expected |
| `npm audit --omit=dev` before / after the lockfile fix | 1 high (follow-redirects 1.16.0) / 0 |

Both counted warnings are Starlette's deprecation of `HTTP_422_UNPROCESSABLE_ENTITY` (one per parametrized
case of `test_service_rejects_non_positive_opening_balance`); pytest-asyncio also prints a notice at start-up
that `asyncio_default_fixture_loop_scope` is unset. Both predate this change and are addressed in task
group 2.

Not yet measured: run times on GitHub-hosted runners (first run happens when the owner pushes; read the job
durations from the Actions tab).
